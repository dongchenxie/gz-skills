# yutong-perf

为广东禹通员工生成**私人的** AI 技术成长教练报告。**不绕过员工本人 = 完全无价值**。**绕过 leader = 让数据真正被用起来**。

## 设计哲学

| 传统考核 | 本 skill |
|---------|---------|
| 老板打分，员工被打 | 员工自己读，AI 教练自己写 |
| 分数公开 / 半公开 | 分数只存在于员工脑子里 |
| 一刀切评分 | 个性化建议（基于 ta 实际做了什么） |
| 区分三六九等 | 识别每个人的「下一个台阶」 |
| 老板做坏人 | 没有坏人，只有数据 + AI 解读 |

**核心承诺**：本 skill 生成的任何文档，**不发给老板、不进 HR 档案、不进入任何决策流程**。它是员工与 ta 的工作数据之间的私人对话。

## 两种输出（都绕过 leader）

### 输出 1：个人技术成长笔记（私发员工本人）

```markdown
# {员工姓名} 的 {YYYY-MM} 技术成长笔记

> 这是你的 AI 教练基于云效项目数据为你写的私人报告。
> 内容只属于你，不需要分享给任何人。

## 本月技术足迹

你在 {n} 个仓库留下了 {n} 个 merged PR，触达 {repoA / repoB} 等 {n} 个项目。
最长一次连续交付是 {n} 天，最长一次评审等待是 {n} 小时。

## 三个我观察到的模式

1. **【你擅长的】** {具体可观察到的优势}
   例：你这月合入的所有 commit 都有清晰的「feat:」「fix:」「refactor:」前缀，commit message 规范度全队排第 1，说明你对代码的「后续读者」很上心。

2. **【值得发扬的】** {发现你做得好的但可能你自己没意识到的事}
   例：你这月修了一个 P0 线上故障，从发现到恢复用了 4 小时，全队最快，且你提交了清晰的根因分析 commit。这种「快 + 复盘」的能力在 DORA 体系里是 elite 团队的核心特征。

3. **【可能的瓶颈】** {中性观察，不是批评}
   例：你这月作为 reviewer 响应 CR 的中位时间是 {n} 小时。这不一定是问题——可能是你太忙了，或者评审任务都堆给另一个人了。值得看一眼是哪种情况。

## 三个建议方向（你可以全选 / 部分选 / 全不选）

### 方向 A：把 {具体事} 推到下一个台阶

- 你这月在 {X 仓库} 做了 {n} 个 {某类} 提交，已经建立了一定肌肉记忆。建议下一步：尝试 {Y 具体动作}。
- 行业参考：{引用 1 句话从参考资料}

### 方向 B：试试 {新工具/新方法}

- 你目前的 AI 工具使用深度估算在 L{n}（{简述}）。如果想试 L{n+1}，可以从这个具体场景开始：{X 仓库 + Y 任务}。
- 不强求——AI 工具是杠杆不是 KPI，用了能帮你省力就试，不喜欢就停。

### 方向 C：{人/项目/技术} 维度的扩展

- 你这月主要在 {当前项目}。如果想接触 {X 项目}（属于公司 {核心业务} 之一），可以：{具体动作}。

## 下月可选的小挑战（自己选 1 个或都不选）

- [ ] {小且具体的 1 件事 1}（例：在 X 仓库主导一次小重构，< 200 行 diff）
- [ ] {小且具体的 1 件事 2}（例：提交一个 PR 级别的「我们怎么用 AI 写代码」内部技术分享）
- [ ] {小且具体的 1 件事 3}（例：用 AI agent 跑通一个完整特性的端到端流程）

> 选 0 个也行。这不是 KPI，是给你自己立的 flag。
> 选 3 个也没人夸你。这是给你自己长肌肉的。

## 行业基准对比（仅供参考）

- **DORA 中位 Lead Time**：你这月 {n} 小时，业内 elite 团队 < 1 小时，高绩效 1 天 - 1 周，行业中位 1 周 - 1 月。
- **变更失败率（revert 占比）**：你这月 {n}%，elite < 5%，高绩效 < 15%，行业普遍 30-45%。
- **评审响应中位**：你这月 {n} 小时，DORA 推荐 < 4 小时。

来源：Accelerate (Forsgren-Humble-Kim, 2018)
```

## 工作流

### 触发方式

- **方式 1**：`/yutong-perf me` — 员工本人触发生成 ta 的私人笔记
- **方式 2**：`/yutong-perf team` — 任何人触发生成团队健康脉搏（leader 也可看，但意义是「系统问题」不是「人的问题」）
- **方式 3**（可选）：月度 cron 自动跑，私发邮件到每个员工

### 数据采集

对每个员工，并行调用：
- `list_change_requests` (per repo) → Lead Time / Deploy Freq
- `list_commits` (per repo) → revert 占比 / 活跃度
- `list_change_request_patch_sets` → CR 修订次数
- `list_change_request_comments` → 评审密度
- `list_workitem_activities` → 任务完成时间

### 产出

- 每个人 → `output/{YYYY-MM}/private/{员工姓名}.md`
- 团队 → `output/{YYYY-MM}/team-pulse.md`

## AI 教练的写作约束

**对员工（私人笔记）**：

1. **三段式结构必须保留**：三个观察 + 三个建议 + 可选挑战
2. **每个观察都要可追溯到具体数据点**（PR 编号、commit hash、revert 次数等）
3. **不空泛夸**：不说"你很棒"、"你很努力"。要具体："你这月修了 X 故障，从发现到恢复 Y 小时，是全队最快"
4. **不空泛批**：不说"你需要更主动"、"你做得不够好"。要指行动："如果你想试 L2 深度 AI 使用，可以从 X 仓库的 Y 任务开始"
5. **建议必须 1 句话能说清**，不写"建议你考虑在未来的工作中尝试更多可能性"这种水话
6. **3 个观察里至少 1 个是真正的好事**，但不能全是彩虹屁——要有真实的、对方能学习的发现
7. **行业基准对比是给员工参考用的，不是羞辱**——"你 18h vs DORA 推荐 4h" 是事实，不评价

**对团队（健康脉搏）**：

1. **不点名**，永远不
2. **只说系统问题**：「评审等待 18h」是系统问题，不是某个 reviewer 慢
3. **每个问题都给可操作的下一步**：不是"需要改进"而是"建议下周会议讨论 X 流程"
4. **行业基准**用表格化展示，方便团队对标

## 已知限制 & 升级路径

- **工作项录入不足**：当前 9 个项目里大部分工作项为空。**行动项**：在团队脉搏里**显式**报告这个数据缺失，让团队自己决定要不要建工作项。这比 leader 喊有用 10 倍。
- **AI 使用检测缺失**：当前无法直接判断哪些 commit 是 AI 写的。**升级路径**：等云效支持读取 AI 元数据，或约定团队统一加 `Assisted-by:` trailer。
- **多 commit 同邮箱问题**：`1225792591@qq.com` 出现 G22 / 林振龙 两个名字。
- **DORA Lead Time 精度**：当前只能算到 CR 维度。
- **Programs API 报 403**：免费版组织不支持。

## Rules

- **绝对禁止**把个人笔记发给老板或任何非本人
- **绝对禁止**在团队脉搏里出现任何员工姓名 / userId / 可识别信息
- **绝对禁止**做排名 / 等级 / 与他人对比
- 每月归档到 `~/.yutong-perf/{YYYY-MM}/`，只保留员工本人能看
- **核心原则**：本 skill 帮员工看清自己，不帮任何人评判员工。

## 为什么这样设计？

员工被打分的最坏结果不是「分数低」——是「分数高但没人信」。当所有人都 90 分时，90 分是侮辱不是认可。

本 skill 的逻辑是：
- 数据是真实的（来自云效）
- AI 解读是中性的（教练视角，不是老板视角）
- 反馈是私人的（只有 ta 看到）
- 成长是自愿的（没有 KPI 压力）

**最后一条规则**（最重要）：

> 任何想用本 skill 重新「做考核」的人，请**直接关掉这个 skill**。
> 本 skill 的存在意义就是**反对考核**。
> 给员工一份真诚的私人成长笔记，比给老板一份 100 人的考核表，对组织更有价值。

## 附录：底层数据模型（仅 skill 维护者看）

员工笔记的三个观察分别从这些数据推导：

**观察类型 1（你擅长的）** — 取该员工**做得最好**的指标：
- commit message 规范度（convention prefix 占比）
- DORA Lead Time 排名（百分位）
- 评审响应速度（百分位）
- 引入线上故障数（最少）
- revert 提交数（最少）

**观察类型 2（值得发扬的）** — 取**该员工做了但 TA 自己可能没意识到的**好行为：
- 复杂重构 commit（涉及 > 5 个文件）
- 跨仓库贡献（同时出现在 2+ repo）
- 故障复盘 commit（root cause analysis 文本）
- 高评审密度的 CR（被讨论最多）

**观察类型 3（可能的瓶颈）** — 取**最不显眼但有改进空间**的指标：
- 评审响应中位（如果 > 8h）
- PR 一次通过率（如果 < 50%）
- revert 占比（如果 > 20%）
- 跨仓库贡献（如果为 0）

每个观察都必须**带一个数据点**（具体数字、PR 链接、commit hash），AI 不允许编造。
